# Presentation Video AI

Starter architecture for a proprietary “presentation-to-video” product. A user uploads a `.pptx` or `.pdf`; the system extracts and rasterizes its pages, synthesizes the source into a coherent storytelling arc, creates independent narrative scenes, generates speech and visual media, and concatenates the scenes into a final MP4.

## Why narrative scenes are independent from pages

Do not ask a video model to generate ten continuous minutes. Scene-level generation gives you:

- isolated retries;
- parallel TTS and rendering;
- deterministic duration control;
- provider swaps without changing the orchestration;
- resumability and artifact-level observability.

The narrative model decides how many scenes the story needs. Related source pages can be merged
into one scene, a dense topic can be split when useful, and repetitive or administrative pages can
be explicitly omitted. Every scene keeps `source_slide_numbers` so its narration and generated
visual remain traceable to the uploaded document.

## Architecture

The repository uses Hexagonal Architecture (Ports and Adapters):

- `domain/`: provider-independent models and contracts;
- `application/`: the video creation use case;
- `infrastructure/`: PPTX/PDF, Pydantic AI, TTS, avatar, and FFmpeg adapters;
- `bootstrap.py`: dependency injection / composition root;
- `api.py`: a small FastAPI demonstration;
- `cli.py`: local execution.

Patterns used:

- **Strategy + Factory:** input handlers are selected by file extension;
- **Adapter:** Pydantic AI, TTS, avatar engines, and FFmpeg implement ports;
- **Dependency Injection:** the pipeline receives interfaces rather than constructing providers;
- **Repository-ready state machine:** job states are explicit and can be persisted later;
- **Pipeline / Template Method:** ingest → script → synthesize → render → assemble;
- **Sidecar pattern:** GPU-heavy avatar generation stays out of the orchestration service.

## Current MVP

The runnable starter creates a video containing:

1. a storytelling script whose scene count is independent from the source page count;
2. an AI-generated narration for each narrative scene;
3. generative speech produced by Gemini TTS through Vertex AI, Replicate, or Pydantic AI;
4. H.264/AAC scene files and a final MP4 generated with FFmpeg.

The pipeline also supports generative visual planning, text-to-image, and image-to-video. Visual
planning and media generation are separate strategies, so either can be swapped without changing
the application service.

The visual workflow is a hybrid storyboard. The narrative model marks each scene as `static` or
`video` according to its role in the story:

- `static`: the best source page is kept unchanged for exact text, numbers, tables, diagrams, and
  conclusions. It is never sent to text-to-image or image-to-video;
- `video`: `prompt -> image -> video` creates a short moving shot with no words, numbers, screens,
  documents, logos, or other readable elements. The clip runs at natural speed and loops until the
  scene narration ends.

The API pauses at the storyboard review, where static pages and video keyframes have distinct
badges. Only video keyframes can be regenerated by prompt. Finalization starts after explicit
approval. The CLI keeps non-interactive behavior and automatically approves the first storyboard.

### Production modes

The creation request accepts `production_mode`:

- `hybrid_presentation` keeps the existing behavior and may preserve source pages when exact
  tables, diagrams, numbers, or wording must remain readable;
- `cinematic_story` treats the document only as factual grounding. It builds a continuous story,
  forces every scene through generated imagery/video, removes source-frame references, and
  replaces any source-slide visual beat with generated imagery. Slides, pages, document layouts,
  captions, and readable interfaces are explicitly forbidden in generated prompts.

The frontend exposes both choices under **Formato visual**. CLI users can select the latter with
`--production-mode cinematic_story`.

In cinematic mode, a narrative scene is no longer a single generated clip. The pipeline
synthesizes its narration first, uses the real audio duration as the timeline, and compiles a list
of contiguous shots. Every shot has:

- a duration of at most eight seconds;
- the exact narration excerpt it represents;
- a story function and required concepts;
- continuity-in and continuity-out state;
- its own image prompt, keyframe, generated video, retry and review card.

The generated clips are trimmed to their planned windows, pass technical visual QA, and are
concatenated once in narrative order. The composer then places that sequence under the original
scene audio. It never loops or slows a model-generated clip.

The declarative workflow v2 exposes the stages `narrative.plan`, `speech.align`, `scenes.plan`,
`visuals.direct`, `prompts.compile`, `rules.validate`, `assets.generate`, `videos.generate`,
`visuals.qa`, and the scene/final composers.

## Generative visual mode

Provider selection is owned by each step in `workflows/presentation-video.yaml`:

- `visual_plan.config.provider: pydantic_ai|replicate` controls structured scene planning;
- `generate_images.config.provider: vertex_ai` generates Google Gemini keyframes for `video` scenes with
  source pages supplied as visual grounding references;
- `generate_images.config.provider: replicate` generates reviewable keyframes for `video` scenes;
- `generate_images.config.provider: slide` uses the original page as a development fallback;
- `animate.config.provider: vertex_ai|replicate|ffmpeg` selects approved-keyframe animation.

`generate_images.provider=slide` cannot be combined with a generative media provider: sending a
source page containing typography to Veo or a Replicate video model would deform its text.

Narration and speech follow the same rule through `narrative.config` and `speech.config`. Provider,
model, model-specific input, timeout and generation behavior live beside the step that consumes
them. Environment files contain only secrets and infrastructure.

If the first script exceeds the requested duration, the same narrative provider receives the
validation errors and the previous script and is asked to condense it.
`narrative.config.max_revisions` controls how many automatic correction calls are allowed.
The initial prompt receives a hard word budget calculated from the workflow input
`target_seconds` and `narrative.config.words_per_minute`.

## Debug mode without paid calls

Use the dedicated example while developing the pipeline or frontend:

```bash
cp .env.debug.example .env
```

With `DEBUG_MODE=true`, the composition root overrides every provider setting before constructing
any external client. Narration and visual planning are deterministic, the original document pages
become the reviewable intermediate images, eSpeak generates local speech, and FFmpeg animates and
assembles the video. No call is made to Replicate, Pydantic AI, OpenAI, or Gemini, even if provider
keys remain in the same `.env`. Restart the backend after changing the flag.

When `DEBUG_REPLAY_JOB_ID` is set, the fixture is read from
`DEBUG_ROOT/<job-id>/output`; its optional intermediate artifacts live in
`DEBUG_ROOT/<job-id>/work`. Replayed jobs are still written to the regular `OUTPUT_ROOT` and
`WORK_ROOT`, keeping fixtures separate from real executions.

`narrative.config.debug.max_scenes` keeps local test jobs short; all source pages are grouped across those scenes,
so a large document still exercises the page-to-story mapping without rendering dozens of clips.
The frontend displays “Modo debug · sem APIs pagas” on jobs created in this mode.

## Concrete visual direction

Static scenes preserve real operational screens, tables, charts, access matrices, lineage graphs,
architecture diagrams, and exact source typography. Generated video scenes instead use concrete
physical action, environments, equipment, materials, and human behavior that work without any
readable element. They explicitly reject screens, documents, typography, isometric miniatures, 3D
dioramas, toy models, symbolic pipes, gates, padlocks, bridges, floating icon grids, and other
conceptual metaphors.

Speech uses the same Strategy pattern, selected by `speech.config.provider`:

- `TTS_PROVIDER=vertex_ai` calls Gemini TTS on Vertex AI with ADC and wraps the returned raw PCM
  audio in a WAV container;
- `TTS_PROVIDER=replicate` calls `google/gemini-3.1-flash-tts` and downloads the WAV output;
- `TTS_PROVIDER=pydantic_ai` uses Pydantic AI's Google provider to call
  `gemini-3.1-flash-tts-preview` through the Gemini Interactions API;
- `TTS_PROVIDER=espeak` remains available as an offline development fallback.

`speech.config.voice`, `language_code`, and `style_prompt` keep delivery consistent
across scenes. The runtime language and tone selected in the UI are added to each TTS request.

Example of a step configured in YAML:

```yaml
- id: generate_images
  uses: visuals.generate
  parallelism: 3
  config:
    provider: replicate
    model: openai/gpt-image-2
    secrets:
      api_token: REPLICATE_API_TOKEN
    model_input:
      aspect_ratio: 1536x1024
      output_format: jpeg
    poll_interval_seconds: 2
    timeout_seconds: 900
```

The YAML declares the credential name, never its value. The matching environment supplies it:

```bash
export REPLICATE_API_TOKEN="r8_..."
```

An additional ready-to-use example is available at
`workflows/presentation-video-pydantic-ai.yaml`. It uses Pydantic AI with Gemini on Vertex AI for
narrative and visual planning, then the native Vertex adapters for image, video and speech. Select
it with:

```bash
export DEFAULT_WORKFLOW=presentation-video-pydantic-ai
export GOOGLE_CLOUD_PROJECT=meu-projeto-gcp
gcloud auth application-default login
```

Replicate model inputs vary by model. `config.model_input` supplies model-specific defaults; the
pipeline adds its runtime fields such as `prompt`. Pin community models as `owner/model:version`.

Gemini 3.1 Flash TTS can occasionally fail to return audio, so the generative adapters retry
transient failures according to `speech.config.max_retries`.

## Google-only mode with Vertex AI

This profile keeps Pydantic AI as the structured-output layer while every paid AI request goes to
a Google model:

| Stage | Model | Location |
| --- | --- | --- |
| Narrative and visual planning | `gemini-3.5-flash` | `global` |
| Reviewable video keyframe | `gemini-3.1-flash-image` | `global` |
| Image-to-video | `veo-3.1-fast-generate-001` | `us-central1` |
| Speech | `gemini-3.1-flash-tts-preview` | `global` |

Pydantic AI selects Vertex AI with the `google-cloud:` model prefix. Image, video, and TTS use
explicit `google-genai` clients with `vertexai=True`, project, and per-service location. This avoids
mixing the Gemini Developer API or Vertex Express Mode into an ADC deployment.

Prepare a billed GCP project, enable Vertex AI, and create local Application Default Credentials:

```bash
gcloud config set project SEU_PROJECT_ID
gcloud services enable aiplatform.googleapis.com
gcloud auth application-default login
gcloud auth application-default set-quota-project SEU_PROJECT_ID
```

The runtime identity needs `roles/aiplatform.user`. By default,
`VERTEX_VIDEO_OUTPUT_GCS_URI` is absent: Veo returns the generated bytes and the backend saves each
clip under `work/<job-id>/clips/`.

Cloud Storage is optional. For more resilient production delivery, enable it, create a bucket in
`us-central1`, grant the runtime identity `roles/storage.objectUser` on that bucket, and uncomment
`VERTEX_VIDEO_OUTPUT_GCS_URI`:

```bash
gcloud services enable storage.googleapis.com

gcloud storage buckets create gs://SEU_BUCKET \
  --location=us-central1 \
  --uniform-bucket-level-access
```

Set the project in the environment, then change the relevant step configs in the workflow YAML to
`provider: vertex_ai` and the desired Google models:

```bash
cp .env.vertex-google-only.example .env
uvicorn presentation_video.api:app --reload
```

Do not add `GOOGLE_API_KEY`, `GEMINI_API_KEY`, or `REPLICATE_API_TOKEN` to this profile. Local
development uses ADC; production on Google Cloud should attach a service account to the workload
instead of storing a service-account JSON key in the repository. Also verify that the project has
Veo quota in `us-central1`.

The avatar port is present, but the default adapter is `NoAvatarRenderer`. A GPU sidecar can later implement MuseTalk, SadTalker, or another authorized talking-head model.

## Prerequisites

- Python 3.11+
- FFmpeg and ffprobe
- LibreOffice / `soffice` for PPTX rendering
- `espeak-ng` only when using the local fallback TTS adapter
- credentials for the selected provider: an API key for hosted API providers, or ADC for Vertex AI

```bash
brew install espeak-ng ffmpeg
```


## API demo

```bash
uvicorn presentation_video.api:app --reload
```

Upload a file:

```bash
curl -X POST http://localhost:8000/v1/videos \
  -F "file=@example.pptx" \
  -F "target_seconds=600" \
  -F "language=pt-BR"
```

Then read the returned job:

```bash
curl http://localhost:8000/v1/videos/<job-id>
```

The demonstration API keeps jobs in memory and uses an in-process asyncio task. For production, replace this boundary with a durable queue/orchestrator such as Temporal, Celery, Prefect, or a managed workflow service, and persist job state in PostgreSQL.

## Recommended production topology

```text
Web/API (CPU)
    |
    v
Job Orchestrator + PostgreSQL + Object Storage
    |
    +--> Narrative Worker (Pydantic AI / LLM)
    +--> TTS Worker (CPU or external provider)
    +--> Avatar Worker (GPU sidecar, optional)
    +--> FFmpeg Render Worker (CPU/GPU)
```

Store source files, slide PNGs, scripts, audio, scene videos, and the final MP4 in object storage. Pass artifact URIs between workers instead of raw binaries.

## Production upgrades

1. Add a multimodal slide-analysis agent for charts and diagrams.
2. Split narrative generation into story architect, scene writer, and reviewer agents.
3. Add actual-audio duration control and an automatic script-compression pass when the final duration exceeds the target.
4. Add word-level timestamps and subtitles.
5. Add an avatar sidecar with explicit face/voice consent, audit trail, and provenance markings.
6. Replace in-memory jobs with durable execution and idempotent steps.
7. Add content validation, malware scanning, upload limits, and tenant isolation.

## Web frontend

The repository now includes a responsive React + TypeScript studio under `frontend/`.

It provides:

- drag-and-drop upload for PPTX and PDF;
- duration, language, audience, and tone configuration;
- live polling and progress by pipeline stage;
- processing timeline for ingestion, script, speech, rendering, and assembly;
- HTML5 video preview;
- final MP4 and JSON script downloads;
- a provider-independent `VideoGateway` interface;
- a production build that can be served directly by FastAPI.

### Single-origin production mode

Compile the frontend first:

```bash
cd frontend
npm ci
npm run build
cd ..
uvicorn presentation_video.api:app --host 0.0.0.0 --port 8000
```

FastAPI detects `frontend/dist`, serves the SPA, and keeps `/v1`, `/health`, `/docs`, and `/openapi.json` available as backend routes.

# Workflow declarativo e estado persistido

O processamento é descrito em
[`workflows/presentation-video.yaml`](workflows/presentation-video.yaml). O arquivo define a
versão, o grafo de dependências, retries, paralelismo e o checkpoint humano de revisão visual.

O runtime possui um executor seguro com:

- dependências `needs` e detecção de ciclos;
- referências `${workflow.inputs.*}`, `${steps.*.outputs.*}` e `${item}`;
- `foreach`, paralelismo controlado, condições booleanas, timeout e retry/backoff;
- checkpoint humano retomável;
- registry explícito de operações, sem execução de Python ou shell vindo do YAML.

O SQLite armazena exclusivamente estado operacional nas tabelas `workflow_runs`,
`workflow_step_runs` e `workflow_events`. PDFs, imagens, áudios, clips, JSONs de conteúdo e vídeos
continuam no filesystem/storage atual. Configure:

```dotenv
WORKFLOW_ROOT=./workflows
DEFAULT_WORKFLOW=presentation-video
WORKFLOW_DATABASE_URL=sqlite:///./work/workflow-state.db
```

Os endpoints `GET /v1/workflows` e `GET /v1/workflow-runs/{job_id}` expõem a definição e o estado
persistido. Após reiniciar o backend, `GET /v1/videos/{job_id}` recupera o estado do SQLite e
`POST /v1/videos/{job_id}/resume` continua usando os arquivos existentes.

Para PostgreSQL, implemente `WorkflowStateRepository` com o driver/ORM escolhido e selecione o
adapter no bootstrap. O executor e os steps não dependem de SQLite; não é necessário alterar o
workflow YAML nem mover os artefatos para o banco.
